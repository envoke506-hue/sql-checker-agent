## 三、关键缺陷：DoubleCheck 防幻觉层过度过滤，导致伪判「完全合规」

共 **13 条**反例的目标规则被大模型正确识别后，又被 `DoubleCheckVerifier` 以「在依据 [n] 原文中无实质支持，判定为模型幻觉并剔除」为由删除：

- **7 条因此最终 0 违规、100 分、伪判合规**：D-02、D-05、D-06、D-08、F-07、F-12、T-10
- 另 6 条虽同样被剔除，但因命中其它规则未导致伪判合规：D-07、F-04、F-11、T-02、T-04、T-06

**这些被剔除的规则本身就是规范原文条款，并非幻觉**，例如：

- 建库规范第 4 条「禁止触发器、存储过程、自定义函数」（D-05 / D-06 的目标规则）；
- 建表规范「字段不要写 CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci」（F-12 的目标规则）；
- 建库规范第 1 条「数据必须使用 innodb 引擎」（D-02 的目标规则）。

判据有两条，均可在本次保留的成果物中复核：

1. **产物内自相矛盾**：这些案例的 `summary` 明确写出了违规（如 D-02：「唯一问题是使用 MyISAM 引擎，违反必须使用 InnoDB 的强制要求」），而 `violations` 为空、`is_compliant=true`；
2. **现场复现**：本次单独重跑 D-05 与 F-12，标准输出稳定打印 `[WARN] [DoubleCheck 拦截] 幻觉误报过滤: 规则 '禁止触发器、存储过程、自定义函数' 在依据 [5] 原文中无实质支持`，两者均复现 100 分 / 0 违规。

> 这与项目设计目标「严禁伪判完全合规」直接冲突：此处并非解析失败，而是防幻觉层把**真规则**当作幻觉删除，属于需要优先修复的缺陷。

## 七、规范原文自相矛盾、判定不一致与数据质量问题

### 7.1 规范文档自身的冲突（需规范维护方确认口径）

| 编号 | 冲突点 | 规范原文 | 影响 |
| --- | --- | --- | --- |
| 1 | 金额/数量字段是否可带本表表名前缀 | 第 5 条示例 `order_money`、第 12 条示例 `order_amount_unit`，与第 16 条「若是本表自己的字段，字段前不需要加表名」直接冲突 | P-01 / P-04 被判不合规（检查器正确）；对照组用例自身标注矛盾 |
| 2 | `db_` 是库前缀还是表前缀 | 第 15 条「**库前缀**统一使用 db_」、建库规范第 2 条「生产**数据库**均以 db_ 开头」 | D-01（`order_info`，表名无 `db_` 前缀）未被报出；README 已登记该分歧 |
| 3 | 数字类型是否必须加 UNSIGNED | 建库规范第 9 条为「**可以**加 UNSIGNED」（推荐性），但建表模板原文写作 `version INT NOT NULL DEFAULT 0`（无 UNSIGNED） | P-02 被判不合规：模型把推荐性条款升级为强制条款 |
| 4 | 布尔字段命名 | 建表规范原文为 `delete` + 「列名尽量用名词」，而知识库切块写作 `is_deleted` | F-06 归因分歧 |

### 7.2 同一系统的判定不一致（规则极性自相矛盾）

- **M-19** 报出「表名 `db_order` 使用了库前缀 `db_`，违反库前缀使用规范」——把**使用** `db_` 判为违规；
- 而 **D-09**（`D-09`）报出「生产表名必须以 `db_` 开头」——把**不使用** `db_` 判为违规；
- 同一系统对同一前缀给出**完全相反**的规则极性，且 **D-01**（真正缺 `db_` 前缀的 `order_info`）两条真缺陷（缺 `db_` 前缀、表名含疑似关键字 `order`）**一条都没报**，反而编造了一条与用例无关的「code 字段长度」规则。这是本次评测中最严重的一致性问题。

### 7.3 跨案例判定不稳定

P-01 与 P-02 的 DDL 都含 `version INT NOT NULL DEFAULT 0` 与 `sort INT NOT NULL DEFAULT 0`：
P-02 因此被判「数字类型必须加 UNSIGNED」，P-01 却未被报出；P-03 也含同样的 `version INT` 写法并判为合规。即同一写法在不同案例中得到不同判定，命中不稳定。
